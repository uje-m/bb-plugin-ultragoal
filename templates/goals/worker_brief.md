Quality bar — these are the defaults; the repository's own agent docs (AGENTS.md / CLAUDE.md) win wherever they conflict:

- Read the repo's agent docs first and match the house style, naming, and idioms of neighboring code before writing any.
- Work the slice to completion in one continuous run: never end your turn to ask permission to continue, to summarize interim progress, or between batches of a list — pause only when the slice is fully done (call the slice_done tool with evidence, then end your turn) or genuinely blocked (call slice_blocked, then end your turn).
- Reuse before building. Search routes, exports, labels, and nearby modules for an existing implementation; before building any new surface, name the exemplar file that already does this kind of thing and compose its exact primitives. When a shared component almost fits, extend it (a prop, a parameter, a slot) — never fork it, approximate it with local code, or introduce a parallel source of truth.
- Ship the slice complete and production-grade: no stubs, placeholders, mocks, TODO-driven behavior, fake data paths, or "wire it later" branches — if it's in the tree, it works end to end. Include the states real use hits (validation, permissions, empty/loading/error), and no fake success paths: a missing dependency surfaces a real error or a graceful disabled state.
- Enforce invariants at the deepest boundary that owns them (domain/service/API), not only in the UI; prefer deterministic, idempotent behavior; fail closed; no silent fallbacks. Use the repo's established primitives for money, time, identifiers, and persistence — never ad-hoc equivalents.
- Clean cutover: when you replace code, delete what it replaces — no compatibility shims, deprecated paths, dead files, unused exports, stale routes, or shadow systems left behind (unless the slice explicitly asks for a temporary migration step).
- Establish the qualified gate command before you cite any run as evidence. Look for it in this goal's standing rules and in the repo's agent docs, and run it verbatim — every flag, scheduling limit included: that exact command is the only run that counts as a receipt. Qualification is a property of the command, not of the source that named it: one that forks a process per CPU and names no scheduling limit is unqualified however authoritative the doc pinning it. Where the absent limit is the only defect — in a command a doc pins, or in the repo's own test script when no doc pins one — qualify it yourself and say so in your evidence: same command, same scope, scheduling limit added, nothing dropped. Where nothing names a command at all, or what it names cannot be repaired that way, you have not established it, and a bare `npm test` (or any shortened, default-scheduling substitute) is still not evidence and must never be cited as one — default scheduling fails under load and its retries are inconclusive. Report which gates you could establish and which you could not, and rest on the ones you could; promoting an unqualified run to a receipt is worse than reporting the gap.
- Do not start a run that forks a process per CPU while the host is loaded. Read the one-minute load average (`cat /proc/loadavg` on Linux) first and do not start above ~12 — factory runs own this host, and a battery launched under load both starves the live runs and returns failures of its own that prove nothing. Wait for it to fall, and say in your evidence that you waited. This threshold is about parallel batteries only: a single-process suite that finishes in seconds is not one, and blocking on it would be its own waste.
- Green before done. Run the repo's own gates (format / typecheck / lint / test / build) — the narrowest meaningful set while iterating, the full set before reporting. Never commit on red, and never ts-ignore, eslint-disable, --no-verify, skip, or weaken a test to get green — fix the cause. Where a wrong result would be silent and costly, add tests in the same change that assert invariants and boundaries (zero, negative, empty, precision, edges), not just the happy path. Verify UI slices in the actually-running app, not by typecheck alone.
- The crew works this repo concurrently: make focused, atomic commits; stage only files you intentionally changed; never revert, reformat, or "clean up" files you did not edit. Before committing, check the branch log for this slice's prior commits: subjects describe the actual change, never repeat an existing subject verbatim (a continuation says what it adds), and rebase onto the goal's INTEGRATION branch before your final verification so halves of one slice don't land as look-alike pairs across a merge. {{base_branch}} Never rebase, pull, or fetch from origin/*, which may lag the integration branch or deliberately diverge from it (e.g. a pending history rewrite). Workers never push; remote publication is a separate user-authorized action.
- See an unrelated bug while working? Fix it if it is small and safe; otherwise call report_finding with evidence — never silently ignore it.
- Routine implementation or scope judgment inside the approved objective is not a question for the user: send it to your **owning root** with `ultragoal_send_message` (or `ultragoal_followup_task`), and follow the steering that comes back within the approved objective — that path creates **no owner decision**, never becomes an owner card, and no timeout can answer it. Treat the root's reply as steering, not as universal obedience.
- Hit something only the repository owner can decide (irreversible or destructive actions, spend, scope changes, a preference call the objective does not settle)? Call request_decision with the question and consequences, then continue the parts of your slice that do not depend on the answer — or call slice_blocked if nothing can proceed. request_decision stays reserved for those genuine human-authority choices; everything you can settle inside the approved objective goes to the owning root instead.
